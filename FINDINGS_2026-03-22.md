# Findings: March 22, 2026

## Executive Summary

The strategy is no longer just a mathematical hypothesis in this repo. After fixing two measurement bugs in the Rust scanner, the live logs now show that:

- some final 5-minute windows are entirely unprofitable
- some final 5-minute windows do become profitable
- profitability can appear late in the window rather than immediately at the open

The strongest live validation so far is the `5:25PM-5:30PM ET` window on March 22, 2026.

## What Was Wrong Before

Two bugs were distorting earlier conclusions:

1. Anchor extraction bug
- raw regex over the Polymarket event HTML could bind the wrong recurring market's anchor
- this caused `A` to repeat across different windows when it should have changed

2. Orderbook interpretation bug
- Polymarket CLOB `book` arrays are not returned best-first
- reading `.asks.first()` without sorting could pick a terrible quote instead of the actual best ask
- this produced fake package costs near `1.98`

## What Was Fixed

In [src/main.rs](c:/Users/sahas/Github%20Repos/prediction-market-btc-arb/src/main.rs):

- live `A` now comes from Polymarket page `__NEXT_DATA__` `crypto-prices` `openPrice`
- closed-window anchors prefer Gamma `events[].eventMetadata.priceToBeat`
- CLOB bids are normalized descending
- CLOB asks are normalized ascending

## Behavioral Interpretation

The pattern now looks like this:

- at the start of the final 5-minute window, the package can still be overpriced
- later in the same window, the relative anchor ordering and leg quotes can move enough to make the correct diagonal cheap enough
- the opportunity is intermittent, not continuous

In the profitable `5:25PM-5:30PM ET` window:

- early rows were mostly `D15+U5`
- profitable rows only appeared once the selected diagonal flipped to `U15+D5`

That matters because the profitable trade is not just "buy the cheaper diagonal." It still depends on correct anchor ordering.

## What This Means For The Project

The project is now in a stronger place:

- the strategy has live empirical support
- the scanner is good enough to detect real profitable moments
- the repo is still not ready for live execution

It is not ready because we still need:

- websocket-based lower-latency market data
- fill-quality and size analysis on profitable windows
- a cleaner live Polymarket-side `B` verification path
- execution, partial-fill handling, and settlement logic

## Recommended Next Steps

1. Capture more full patched windows and measure:
   - how often profitability appears
   - how long positive-edge periods last
   - how much size is really fillable at positive edge
2. Add websocket logging for Polymarket books.
3. Build a replay and summary layer over `data/live/pair_scans.ndjson`.
4. Only then consider an execution path.
